# 自适应并发控制器 V3 设计

## 背景

V2 实现存在三个架构级缺陷导致"并发度降到 0/1 且永不恢复"：

1. **冷却期语义倒置**：冷却期阻止成功累积（恢复），不阻止失败累积（进一步下降），导致短时间内连续 429 造成指数坍缩
2. **利用率门控死锁**：`limit > max/2` 时需 `limitReached=true` 才恢复，但低并发时无人排队，永久锁死
3. **max=0 输入无防护**：`init({ max: 0 })` 导致 `deriveProfile(0,0)` 产生 NaN 阈值，状态机冻结

V3 从根因修复，同时保持水位梯度参数体系和事件驱动架构不变。

## 算法

### 状态机

```
                 success ← 1  ----------------------→ 429
                 ↓                                        ↓
    consecutiveSuccesses++                      consecutiveSuccesses = 0
    consecutiveFailures = 0                     if 冷却期内: return
                                                if 429:
    if 连续成功 >= climbThreshold:                  currentLimit -= 1
        if limit < max:                              consecutiveFailures = 0
            limit += 1                               进入冷却期(dropCooldownUntil)
            consecutiveSuccesses = 0
        else:                                      if 5xx/net:
            consecutiveSuccesses /= 2               consecutiveFailures++
        syncToSemaphore()                         if 连续失败 >= dropThreshold:
                                                      limit -= 1
                                                      consecutiveFailures = 0
                                                      进入冷却期
                                                  syncToSemaphore()
```

### 参数推导（deriveProfile）

沿用 V2 的梯度公式，去掉 `safeZone` 和 `keepRatio`：

```
level    = currentLimit / max
capacity = min(1, log2(max) / 7)

climbThreshold = max(2, round(2 + capacity*2 + level*2))      // 连续成功多少次 +1
dropThreshold  = max(1, round(5 - capacity*2 - level*2))      // 连续 5xx 多少次 -1
cooldownMs     = round(10000 + level * 10000)                  // 下降后冷却期
```

| max | limit | climbThreshold | dropThreshold | cooldown |
|-----|-------|---------------|--------------|----------|
| 3 | 1 | 3 | 4 | 13s |
| 3 | 2 | 4 | 3 | 17s |
| 3 | 3 | 4 | 3 | 20s |
| 5 | 1 | 3 | 4 | 12s |
| 5 | 3 | 4 | 3 | 16s |
| 5 | 5 | 5 | 2 | 20s |
| 6 | 1 | 3 | 4 | 12s |
| 6 | 3 | 4 | 3 | 15s |
| 6 | 6 | 5 | 2 | 20s |
| 10 | 1 | 3 | 4 | 11s |
| 10 | 3 | 4 | 3 | 13s |
| 10 | 5 | 4 | 3 | 15s |
| 10 | 7 | 4 | 3 | 17s |
| 10 | 9 | 5 | 2 | 19s |
| 10 | 10 | 5 | 2 | 20s |
| 20 | 5 | 4 | 3 | 13s |
| 20 | 10 | 4 | 3 | 15s |
| 20 | 15 | 5 | 2 | 18s |
| 20 | 20 | 5 | 2 | 20s |

### 和 V2 的关键差异

| 维度 | V2 | V3 |
|------|----|----|
| 爬升门控 | safeZone + limitReached 双锁 | 无门控 |
| 冷却期语义 | 阻止成功累积 | 阻止进一步下降 |
| 冷却期内 429 | 继续削减 | 被拦截 |
| 429 下降方式 | `floor(x * (1-1/x))` 乘法 | `x - 1` 固定 |
| 爬升失败时计数器 | 清零 | 保留一半（满额时） |
| 死锁风险 | 50% 空间 | 0% |
| max=0 防护 | 无 | 入口 `Math.max(max, 1)` |

## 场景行为分析

以下场景均以 `max=10` 为例（另有 max=1/3/20 专项场景）。

### S1 — 正常启动

**输入**：40 次连续成功，每次间隔 1s

**过程**：`currentLimit` 始终 = 10。每 5 次成功后 `at max`，计数器保留一半。无波动。

**结论**：正常情况下并发度保持在 max，不会出现 v2 中"幽灵爬升"问题（因为已经到顶）。

### S2 — 偶发 429

**输入**：10 次成功 → 1 次 429 → 20 次成功

**过程**：
```
t=0s:  limit=10, 正常
t=11s: limit=10 → 429 → limit=9, 冷却期 20s
t=16s: limit=9, 5 次连续成功 → limit=10 (恢复)
t=16~31s: limit=10, 正常运行
```

**结论**：一次 429 导致 limit 下降 1 格，5 次成功（5s）后完全恢复。V2 中此场景会卡在 limit=9 死锁区。

### S3 — 低负载（60s 间隔）

**输入**：30 次成功，每次间隔 60s

**过程**：`currentLimit` 始终 = 10。每 5 个请求（5 分钟）触发一次 `at max`。无异常波动。

**结论**：低负载时并发度不下降。V2 中可能存在幽灵爬升问题，V3 中因为已在 max 所以不爬。

### S4 — 高负载（0.5s 间隔密集成功）

**输入**：50 次成功密集到达

**过程**：同 S1，limit 始终在 max。

**结论**：密集成功不会导致过度反应。

### S5 — 连续 429 攻击（最极端）

**输入**：10 次连续 429，间隔 0.2s

| V2 行为 | V3 行为 |
|---------|---------|
| limit: 10→1（9 次砍完，0.9s） | limit: 10→9 后冷却期 20s，后续 9 个 429 全部拦截 |
| 恢复: 冷却期 10-20s + 安全区锁死 | 恢复: 冷却期后立即可以爬升 |

**结论**：V3 将连续 429 攻击从"指数坍缩"变为"单次下降 + 保护期"。即使上游持续返回 429，并发度每 20s 最多降 1 格。

### S6 — 间歇性 429 穿插成功

**输入**：模式 `success × 3 → 429 → success × 3 → 429 → ...` 重复 15 次

**过程**：
```
t=0s:   limit=10
t=7s:   429 → limit=10→9, 冷却期 20s
t=7-27s: 冷却期内 429 被拦截，成功正常累积
t=14s:  limit=9→10 (恢复)
t=20s:  冷却期结束
t=21s:  429 → limit=10→9 (新一轮)
```

**结论**：间歇 429 不会导致级联下降。每轮需要 20s 冷却期 + 5 次成功恢复。即使 429 频率高（15 次/105s），limit 在 9-10 之间稳定振荡。

### S7 — 持续 5xx

**输入**：20 次连续 5xx，间隔 1s

**过程**：
```
t=2s:   2 次 5xx → limit 10→9, 冷却期 20s
t=3-22s: 冷却期内所有 5xx 被拦截
```

**结论**：持续 5xx 每 20s 最多降 1 格。最坏情况：20×20 = 400s 才能从 10 降到 1。V2 中频繁 5xx 也会加速下降。

### S8 — 5xx 后恢复

**输入**：8 次连续 5xx → 40 次成功

**过程**：
```
t=2s:   2 次 5xx → limit 10→9, 冷却期 20s
t=3-8s: 冷却期内 5xx 被拦截
t=22s:  冷却期满，5 次成功 → limit 9→10 (恢复)
```

**结论**：5xx 后恢复速度 = 5 次成功。冷却期内成功正常累积（不受冷却期影响）。

### S9 — 混沌混合

**输入**：`success × 2 → 429 → success × 2 → 5xx × 2 → success × 2 → networkError → success × 3 → 429 × 2 → success × 4 → 5xx → 2xx_retry → 429 → success × 3`（两轮）

**过程**：
```
t=3s:  limit=10→9 (429)
t=15s: limit=9→10 (4 successes)
t=22s: limit=10→9 (429, cd still active from new? no)
...
final: limit=7
```

**结论**：混沌场景长期运行后 limit 有净下降趋势（因为误差和 2xx_retry 的叠加 > 成功恢复），但下降速度可控（1 格约需 15-20s 净负信号）。极限情况下 10→1 需要约 3-5 分钟。这比 V2 的 < 10 秒好得多。

### S10 — max=3 偶发 429

**输入**：`success × 3 → 429 → success × 3 → 429 → ...`

**过程**：
```
t=4s: 429 → limit=3→2, 冷却期 20s
t=9s: 4 次成功 → limit=2→3
t=24s: 429 → limit=3→2 (冷却期已过)
```

**结论**：max=3 时每次 429 强制降 1/3 容量，但冷却期保护防止了 V2 中的 3→2→1 快速坍缩。恢复需 4 次成功。

### S11 — max=1 极限

**输入**：success → 429 → 3 × success → 5xx → success

**过程**：
```
t=1s: limit=1, 成功
t=2s: 429 → limit=max(1-1,1)=1 (无法再降)
t=3-5s: 成功累积，climbThreshold=4, at max=1, 计数器保留 2
t=6s: 5xx → 冷却期内 (429 设置的 20s cd) → 拦截
```

**结论**：max=1 时 limit 无法降低（已是最低），冷却期正常保护。这是一个退化情况，算法行为合理。

### S12 — max=20 偶发 429

**输入**：密集成功 → 1 次 429 → 更多成功

**过程**：
```
t=5.5s: limit=20→19 (429), 冷却期 20s
t=8.0s: 5 次成功 → limit=19→20 (恢复)
```

**结论**：大 max 时恢复速度与小 max 一样（都是 climbThreshold=5 次连续成功）。但容量损失比例小（1/20 = 5%）。

### S13 — 非并发错误

**输入**：`success → 200 body error → 400 → 401 → success × N`

**过程**：所有 2xx/4xx 错误在 `transitionFailure` 入口被过滤，不影响任何状态。成功计数不受干扰。

**结论**：非并发错误（客户端 4xx、上游 2xx body error）被正确过滤，不会误触发退避。

### S14 — 信号量超时/队列满

**输入**：`429(超时) → success × 2 → 429(队列满) → success × 2`

**过程**：两次 429 均触发降格。若第二次在第一次的冷却期内，则被拦截。

**结论**：信号量超时和队列满被 `orchestrator` 层转为 `statusCode: 429`，与上游 429 同等处理。

### S15 — 从 limit=1 完全恢复

**输入**：50 次连续成功（模拟从灾难性降低恢复）

**过程**：
```
t=3s:  limit=1→2 (3 successes)
t=6s:  limit=2→3 (3 successes)
t=10s: limit=3→4 (4 successes)
t=14s: limit=4→5 (4 successes)
t=18s: limit=5→6 (4 successes)
t=22s: limit=6→7 (4 successes)
t=26s: limit=7→8 (4 successes)
t=31s: limit=8→9 (5 successes)
t=36s: limit=9→10 (5 successes)
```

**结论**：从 1 恢复到 10 需要 36 次成功（36s@1rps）。高位时更保守（limit=8→9→10 各需 5 次成功），低位时更激进（limit=1→2→3 只需 3 次）。V2 中此场景卡在 limit=6 死锁。

### S16 — 冷却期边界

**输入**：`429 → 5s 后 429(冷却期内) → 5s 后 5xx(冷却期内) → success × 2 → 冷却期满 429 → success × 5`

**过程**：
```
t=1s:   429#1 → limit=10→9, 冷却期 20s
t=6s:   429#2 → 冷却期内, 拦截
t=11s:  5xx → 冷却期内, 拦截
t=16s:  success → 正常累积
t=22s:  429#3 → 冷却期满 (cooldownUntil=21s, now=22s) → limit=9→8
t=27-47: 5 次成功 → limit=8→9
```

**结论**：冷却期边界行为正确——期满后的第一个失败立即触发下降。成功在任何时刻都不受冷却期影响。

### S17 — 满载时继续成功

**输入**：30 次成功，limit 一直在 max=10

**过程**：每 5 次成功后 `at max, counter retained 2`。连续成功不会造成问题。

**结论**：满载时计数器在半衰减状态下持续循环，不会触发意外行为。这是正常的稳态振荡。

### S18 — 关闭后重新开启

**输入**：禁用自适应（semaphore 被设置为 maxConcurrency=0）→ 重新启用（limit 重置为 max=10）→ 30 次成功

**过程**：
```
init: limit=10, max=10 (通过 Math.max(max, 1) 防护)
恢复: 30 次成功，limit 始终 = 10
```

**结论**：重新启用自适应时 limit 从 max 启动（乐观启动），与初始启动行为一致。

### S19 — 极低流量（5 分钟间隔）

**输入**：30 次成功，每次间隔 300s

**过程**：limit 始终 = 10。冷却期早已过期（5 分钟 > 20s）。每次失败独立处理。

**结论**：极低流量时算法退化到逐事件处理，但行为仍然合理。cooling 期在这种场景下形同虚设（间隔远大于冷却期），不影响正确性。

### S20 — 网络中断后恢复

**输入**：8 次 net error → 40 次成功

**过程**：
```
t=2s:  2 次 net → limit 10→9, 冷却期 20s
t=3-8s: 冷却期内 net 被拦截
t=10-18: 5 次成功 → limit 9→10
```

**结论**：与 S8（5xx 恢复）行为一致。网络错误走 5xx 路径（连续失败退避），被冷却期保护。

## 参数合理性分析

### 上升速度

| max | 从 1 恢复到 max | 成功次数 | 耗时@1rps |
|-----|----------------|---------|----------|
| 3 | 1→3 | 7 | 7s |
| 5 | 1→5 | 17 | 17s |
| 6 | 1→6 | 21 | 21s |
| 10 | 1→10 | 36 | 36s |
| 20 | 1→20 | ~78 | 78s |

恢复时间与 max 成正比（约 4×max 次成功），这是合理的：更大的 max 意味着需要更多证据来确认系统健康。

### 下降速度

| max | 429 坍缩到 1 | 最坏时间 |
|-----|-------------|---------|
| 任意 | 每 10-20s 降 1 格 | max × (10-20)s |
| 10 | — | 100-200s |
| 6 | — | 60-120s |
| 3 | — | 30-60s |

V2 中此值约为 0.2s × 9 = 1.8s（10→1）。V3 下降速度降低了 100 倍。

### 升降比

| limit=5 | 上升 | 下降()429 | 下降(5xx) | 比率 |
|---------|------|----------|----------|------|
| climb=4 | 4 次成功 | 1 次 429 | 3 次 5xx | 1:4 or 3:4 |

高位时 (limit=10)：
| climb=5 | 5 次成功 | 1 次 429 | 2 次 5xx | 1:5 or 2:5 |

上升代价是下降代价的 1.5-5 倍，保持"上升慢、下降快"的传统 AIMD 不对称性，但不再有死锁。

## 极端场景分析 (E1-E21)

### E1 — 冷却期边界精准打击（最密下降模式）

**输入**：429 每 22s 一次（刚好在冷却期边界），中间只有 1 次成功。

**过程**：
```
t=0:  429 → 10→9  cd=20s
t=22:  429 → 9→8  (cd 期满)  cd=19s
t=44:  429 → 8→7  cd=18s
...
t=198: 429 → 2→1  cd=12s
t=220: 429 → 1→1  (clamped)
```

**结论**：极限情况下 limit 从 10 漂移到 1 约需 200 秒。每次 429 降 1 格，1 次成功不足以爬升（需要 3-5 次）。这是 AIMD 不对称性的固有限制。但比 V2（2 秒坍缩）慢 100 倍，且仅当 429 频率精确对齐冷却期边界时发生。实际生产中几乎不会出现。

**风险评估**：低。即使发生也是渐进式下降，给运维留出足够的检测和干预时间。

### E2 — 慢请求（60s）+ 快失败（1s）交错

**输入**：5 次快成功 → 1 次 429 → 60s 慢成功 → 429 → 慢成功 → ...

**过程**：
```
t=10:  429 → 10→9
t=70:  慢成功#1 → s=1/5
t=71:  429 → 9→8  (重置成功计数)
t=131: 慢成功#2 → s=1/5
t=132: 429 → 8→7
...
t=253: 慢成功#4 → s=1/4, limit=6
```

**结论**：慢请求场景下，每次成功积累被 429 打断，limit 净下降。但这反映的是真实信号——50% 失败率的 provider 应该降低并发度。253s 内从 10 降到 6（40% 削减），与 50% 失败率基本匹配。

**风险评估**：低。算法行为与失败率成比例，符合设计意图。

### E3 — max=100 大规模

**输入**：200 次密集成功 → 1 次 429 → 50 次恢复成功。

**过程**：
```
t=20:   429 → 100→99  cd=20s
t=23:   5 次成功 → 99→100  (5s 恢复)
```

**结论**：`deriveProfile` 在大 max 下参数收敛（climbThreshold=6, dropThreshold=1, cooldown=20s）。恢复仅需 5 次成功（5s），容量损失 1%。算法在大规模下表现良好。

**风险评估**：无。

### E4 — max=2 最小非平凡值

**输入**：5 次成功 → 429 → 4 次成功 → 429 → 3 次 5xx。

**Profile**：limit=1→climb=3,drop=4,cd=15s；limit=2→climb=4,drop=3,cd=20s。

**过程**：
```
t=6:  429 → 2→1  cd=20s
t=12: 3 次成功 → 1→2
t=15: 429 → cd 内拦截
t=18-24: 3 次 5xx → 全部 cd 内拦截
```

**结论**：max=2 时 429 降 50% 容量，但冷却期保护了进一步下降。3 次成功即可恢复。

**风险评估**：低。

### E5 — 升降振荡

**输入**：`success×5 → 429 → success×5 → 429(冷却期内) → success×5 → 429(期满)` 循环。

**过程**：limit 在 9↔10 之间健康振荡。429 在冷却期内被拦截不会造成连续下降。

**结论**：这是正常的稳态行为——limit 在 max 附近小幅波动。

**风险评估**：无。

### E6 — retryRuleMatched 误触发

**输入**：`success×3 → 2xx+retry → success → 2xx+retry×2 → success×5`。

**过程**：
```
t=4:  200 body err+retry → f=1/2
t=5:  success → 重置 f=0
t=6:  200 body err+retry → f=1/2
t=7:  200 body err+retry → f=2/2 → 10→9 cd=20s
t=8-12: 5 次成功 → 9→10
```

**结论**：retryRuleMatched 会触发退避，但需要连续 2 次（中间不能被成功打断）。如果上游所有请求都 retryRuleMatched（全部 body error），第一次 drop 后冷却期保护后续 20s 内不再下降。

**风险评估**：中。retryRuleMatched 的语义是"此错误值得重试"，计入退避是合理的。但如果大量非并发错误被误标记为 retryRuleMatched，会造成不必要的退避。这是上游信号质量问题，不是算法问题。

### E7 — 持续 5xx 慢恢复（模拟上游宕机后恢复）

**输入**：11 次 5xx（跨越多轮冷却期） → 40 次恢复成功。

**过程**：
```
t=2:   2 次 5xx → 10→9  cd=20s
t=24:  冷却期满 → 2 次 5xx → 9→8  cd=19s
t=57:  冷却期满 → 2 次 5xx → 8→7  cd=18s
t=90:  冷却期满 → 2 次 5xx → 7→6  (dropT=3 for limit=7)
       ...限继续下降...
t=113: 开始恢复 → 7→8→9→10 (约 36s)
```

**结论**：持续 5xx 期间，每 20-30s 降 1 格。一旦成功恢复，36s 内回到 max。总中断时间约 140s。

**风险评估**：低。

### E8 — 批量并发完成（同一 tick）

**输入**：10 个请求在 t=0 同时完成 → 429 → 429×3（间隔 21s 对齐 cd 边界）→40 个请求同时完成。

**过程**：
```
t=0:   10 个成功 → 连续爬升（同 tick 按 event loop 顺序处理）
t=0:   429 → 10→9
t=21:  429 → 9→8
t=41:  429 → 8→7
t=60:  429 → 7→6
t=60:  40 个成功同时完成 → 6→7→8→9→10 (同 tick 快速爬升)
```

**结论**：同一 tick 内多个 success 会快速累积并触发多次爬升。这是正确的——大量同时完成的成功是系统健康的有力证据。Node.js 单线程保证不会有并发写入问题。

**风险评估**：无。

### E9 — 系统时钟跳跃（NTP 校正）

**输入**：429（t=1s，cd=21s）→ 时钟向后跳 3600s → 更多请求。

**过程**：
```
t=1:    429 → 10→9  cd=21s
t=3601: cd 早已过期 → 成功正常累积 → 5 次 → 9→10
```

**结论**：`Date.now()` 用于冷却期判断，时钟跳跃后 cd 自然过期，行为正确。

**风险评估**：无。

### E10 — 无流量 1 小时后突发 429

**输入**：3600s 无流量 → 429 → 5 次成功 → 429。

**过程**：
```
t=3600: limit=10 → 429 → 9  cd=20s
t=3625: 5 次成功 → 9→10
t=3626: 429 → 10→9  (新一轮)
```

**结论**：长时间无流量时 limit 保持在 max。后续突发 429 正常处理。

**风险评估**：无。

### E11 — max=50/100/500/1000 参数推导

| max | climb(low/mid/high) | drop(low/mid/high) | cooldown(low/mid/high) |
|-----|--------------------|--------------------|----------------------|
| 50 | 4/5/6 | 3/2/1 | 12/15/20s |
| 100 | 4/5/6 | 3/2/1 | 12/15/20s |
| 500 | 4/5/6 | 2/2/1 | 12/15/20s |
| 1000 | 4/5/6 | 2/2/1 | 12/15/20s |

**结论**：`capacity = min(1, log2(max)/7)` 有效限制了参数发散。climbThreshold 收敛到 6，dropThreshold 收敛到 1，cooldown 收敛到 12-20s。算法在所有 max 范围（1~1000+）内保持可控。

**风险评估**：无。

### E12 — 突发洪峰 + 连续 429 + 恢复

**输入**：30 次密集成功（0.1s 间隔）→ 5 次 429（0.1s 间隔）→ 20 次稀疏成功（21s 间隔）。

**过程**：
```
t=3:   30 次成功 → limit 保持 10
t=3.1: 429#1 → 10→9  cd=20s
t=3.2-3.5: 429#2-#5 → 冷却期内全拦截
t=24-108: 5 次成功 → 9→10  (稀疏间隔，但累积有效)
```

**结论**：突发 5 次 429 只触发 1 次下降，其余 4 次被冷却期拦截。稀疏恢复有效——成功计数不因间隔大而衰减。

**风险评估**：无。

### E13 — 双 provider 同时 429

**输入**：两个 provider 同时经历相同的 429 模式。

**过程**：两者独立、行为完全一致。各自由 10→7（3 次 429 对齐 cd 边界），各自独立恢复到 10。

**结论**：per-provider 状态隔离正确。

**风险评估**：无。

### E14 — retryRuleMatched 洪水

**输入**：15 次连续 2xx+retryRuleMatched。

**过程**：
```
t=1-2: 2 次 → 10→9  cd=20s
t=3-15: 13 次 → 冷却期内全拦截
```

**结论**：第一次 drop 后冷却期拦截了后续 13 次。如果这种模式持续（冷却期满后继续来 retry），每 20s 才降 1 格。

**风险评估**：低。

### E15 — 冷却期内大量成功（关键验证）

**输入**：1 次 429 → 80 次密集成功。

**过程**：
```
t=1.0: 429 → 10→9  cd=20s
t=1.1-1.5: 5 次成功 → 9→10  (冷却期内! 成功累积不受冷却期影响)
t=1.6+: 持续在 max
```

**结论**：这是 V3 和 V2 的核心差异——冷却期不阻止成功累积。429 后仅 0.5 秒（5 次成功）就完全恢复。V2 中这 5 次成功会被丢弃。

**风险评估**：无。

### E16 — max=3 连续 5xx

**输入**：20 次连续 5xx。

**Profile**：limit=3→dropT=3, limit=2→dropT=3。

**过程**：
```
t=3:   3 次 5xx → 3→2  cd=20s
t=4-20: 17 次 → 冷却期内全拦截
```

**结论**：max=3 时 5xx 需要连续 3 次才触发下降（dropThreshold=3），比高位更保守。下降后冷却期保护了剩余 17 次。

**风险评估**：无。

### E17 — 精准边界循环（最密下降，同 E1 细化）

**输入**：与 E1 相同的 22s 精准边界。

**附加观察**：到达 limit=1 后，429 不再降（clamped），climbThreshold=3。如果持续 429@22s：
```
t=N:   limit=1, 429 → 1→1  cd=11s
t=N+3: 3 次成功  → 1→2
t=N+22: 429 → 2→1  cd=12s  (振荡 1↔2)
```

**结论**：即使最极端的精准边界场景，limit 也只在 1↔2 之间振荡，不会彻底锁死。需要同时满足"每 22s 一次 429 + 间隔内仅 1 次成功"两个条件才能维持下降趋势，实际中概率接近 0。

**风险评估**：极低。

### E18 — 失败被成功打断（dropThreshold 边界）

**输入**：`5xx → success → 5xx → success → 5xx → 5xx`。

**过程**：
```
t=1: 5xx → f=1/2
t=2: success → f=0  (重置!)
t=3: 5xx → f=1/2
t=4: success → f=0  (重置!)
t=5: 5xx → f=1/2
t=6: 5xx → f=2/2 → 下降!
```

**结论**：成功插入失败序列中会重置连续失败计数器。只有在纯连续失败序列中才触发下降。这是正确的——间歇性失败不应该触发退避。

**风险评估**：无。

### E19 — 爬升中冷却期内 429 被拦截

**输入**：`429 → 4 次成功 → 429(冷却期内) → 1 次成功（触发爬升）→ 429(新冷却期内)`。

**过程**：
```
t=1:  429#1 → 10→9  cd=20s
t=2-5: s1-s4 → s=4/5
t=6:  429#2 → cd 内拦截! (保护了即将触发的爬升)
t=7:  s5 → 4→5=5/5 → 9→10  (爬升成功!)
t=12: 429#3 → cd 内拦截
t=21: 429 可能触发新下降...
```

**结论**：V3 冷却期拦截失败，保护了正在积累的成功计数。V2 中 429#2 会重置成功计数并再次下降。

**风险评估**：无。

### E20 — 万次成功 counter overflow

**输入**：10000 次成功，0.001s 间隔。

**过程**：`successes` 在半衰减（`//= 2`）下保持在 2-4 之间循环，永远不会增长到危险值。limit 始终 = 10。

**结论**：`successes //= 2` 有效地防止了计数器无限增长。即使 100 万次成功，计数器也在个位数范围。JavaScript number 无溢出风险（浮点数上限 ~1.8e308）。

**风险评估**：无。

### E21 — limit=1 冻结后恢复（无冷却期干扰）

**输入**：从 limit=1 开始，50 次连续成功。

**过程**：
```
t=3:  3 次成功 → 1→2
t=6:  3 次成功 → 2→3
t=10: 4 次成功 → 3→4
t=14: 4 次成功 → 4→5
t=18: 4 次成功 → 5→6
t=22: 4 次成功 → 6→7
t=26: 4 次成功 → 7→8
t=31: 5 次成功 → 8→9
t=36: 5 次成功 → 9→10
```

**结论**：共需 36 次成功恢复。低位恢复快（3 次/格），高位恢复慢（5 次/格），符合水位梯度设计。

**风险评估**：无。

## Edge Cases 总结

| 场景 | 行为 | 风险 |
|------|------|------|
| max=0 | `Math.max(max, 1)` 防护 | 无 |
| max=1 | limit 无法下降，冷却期正常 | 退化正常 |
| max=2 | 429 降 50% 但冷却期保护 | 低 |
| max=1000 | 参数收敛，行为正常 | 无 |
| 精准边界循环 (E1/E17) | limit 从 10 缓慢漂移到 1（~200s），最慢下降 | 极低（需精确时序） |
| 慢请求+快失败 (E2) | limit 净下降与失败率成比例 | 低 |
| 冷却期内大量成功 (E15) | 冷却期内成功正常累积，快速恢复 | 无 |
| retryRuleMatched 洪水 (E14) | 冷却期保护下降速度 | 低 |
| 系统时钟跳跃 (E9) | Date.now() 免疫 | 无 |
| 万次成功 (E20) | 计数器不溢出 | 无 |
| 批量同 tick 完成 (E8) | 快速爬升，行为正确 | 无 |
| 所有请求都失败 | 每 cooldownMs 降 1 格，最低到 1 | 可控 |
| 非并发错误洪水 | 全部过滤 | 安全 |
| 信号量频繁超时 | 按 429 处理，受冷却期保护 | 可控 |

## 防护清单

| # | 类型 | 位置 | 修复 |
|---|------|------|------|
| 1 | Guard | `init()` | `config.max = Math.max(config.max, 1)` |
| 2 | Guard | `syncProvider()` | `p.max_concurrency = Math.max(p.max_concurrency, 1)` |
| 3 | Guard | `syncProvider()` existing | `currentLimit = Math.max(Math.min(currentLimit, max), 1)` |
| 4 | Guard | `syncToSemaphore()` | 保留 `Math.max(currentLimit, 1)` |
| 5 | Algorithm | `transitionSuccess()` | 移除 safeZone/limitReached 门控 |
| 6 | Algorithm | `transitionFailure()` | 429 固定 -1（移除乘法衰减） |
| 7 | Algorithm | `transitionFailure()` | 冷却期前置检查（阻止下降） |
| 8 | Algorithm | `transitionSuccess()` | 满额时保留一半计数器 |
| 9 | Algorithm | `transitionFailure()` | 冷却期拦截后不累积 failures |
