### 根因深挖

**回退 1: Spec 3 轮评审**
- **表面原因**: Spec 初版不够完整，缺少关键设计细节
- **根本原因**: "映射原因追踪"看似简单的字段传递需求，实际涉及 6 个映射值 × 2 种存储路径 × 12 个数据消费者的矩阵。这类"跨层穿透"需求的信息密度高于直觉判断
- **可预防性**: 中等。第一轮 spec 写完后如果自检六要素覆盖矩阵（已有规范），可以减少一轮回退。但 3 轮对于一个跨后端+前端的需求属于合理范围

**回退 2: parseMappingReason 格式 bug**
- **表面原因**: 前端 `parseMappingReason()` 解析 pipeline_snapshot 时用了 `parsed.stages` 访问数组，但 DB 存的是纯 JSON 数组而非 `{stages: [...]}`
- **根本原因**: Plan 和 Spec 中都描述 pipeline_snapshot 为"JSON 字符串"，但未明确其顶层结构是数组还是对象。Plan 中 `parseMappingReason()` 的伪代码直接用了 `parsed.stages` 而未质疑。编码实现者按 plan 的伪代码逐字实现，plan 的错误直接传播到代码
- **可预防性**: 高。编码前用一个真实 pipeline_snapshot 样例验证解析逻辑即可发现。或在 TDD 阶段用 DB 中实际存在的 snapshot 格式构造测试数据

## 2. 评审有效性

### 评审拦截分析

| 评审类型 | 轮次 | 发现问题数 | 拦截关键问题 | 有效拦截 |
|---------|------|----------|------------|---------|
| Spec 评审 | 3 | — | Spec 完整性逐步提升 | 是 |
| Plan 评审 | 1 | 0 MUST FIX, 2 LOW | 无关键问题，plan 与代码库引用一致 | 是（确认 plan 可行） |
| 编码评审 | 1 | 1 MUST FIX | parseMappingReason 格式 bug | **是** |
| 测试评审 | 1 | 0 MUST FIX, 2 LOW + 2 INFO | 无关键问题 | 是 |

### 编码评审拦截详情

**编码评审发现的关键 bug**: `parseMappingReason` 期望 `parsed.stages`（对象包裹数组），但 DB 中 `pipeline_snapshot` 实际存储纯 JSON 数组。

**为什么 TDD 没拦截**:
- TDD 的 `parseMappingReason` 测试（`router/tests/parse-mapping-reason.test.ts`）在 router 包内重新实现了函数逻辑，构造的测试数据用的是开发者脑中的格式（`[{stage: "routing", ...}]`），而非从 DB 中读取的真实格式
- 测试数据和实现代码犯了同样的假设错误，因此测试通过但 bug 存在

**为什么编码评审能拦截**:
- 评审者独立读取了 DB 中实际存储的 pipeline_snapshot 数据（或检查了 `insertRequestLog()` 的序列化逻辑），发现顶层是纯数组
- 这是评审的真正价值：独立于实现者的思维路径重新验证

### 评审 ROI 评估

| 维度 | 评价 |
|------|------|
| Spec 评审 3 轮是否过多？ | 适中。跨 12 个消费者的需求需要充分规格化，3 轮确保了零规格遗漏 |
| Plan 评审 1 轮是否充分？ | 是。Plan 评审验证了代码引用准确性，通过率高说明 Spec 打下了好基础 |

| 测试评审 1 轮是否充分？ | 是。测试覆盖完整（9 AC 全覆盖），无需修复 |

### 缺口分析

**已识别缺口 1: 数据格式一致性验证**
- parseMappingReason 格式 bug 表明：**缺少"实现代码与 DB 实际存储格式一致性"的自动验证**
- L1 gate 只检查编译、lint、测试通过，无法检测"前端解析器假设的数据格式与 DB 实际存储格式不一致"
- 建议：对 DB JSON 字段的解析函数，测试中应直接读取 DB 中的真实数据样本或使用与 DB 序列化相同的构造方法

**已识别缺口 2: 跨包测试同步**
- `parseMappingReason` 的测试在 `router/tests/` 中用本地副本而非 import 前端实现。这意味着前端代码变更不会触发 router 包的测试失败
- 这是已知基础设施限制（跨包 import 不可行），但在复盘记录

**无遗漏场景**: gate 脚本覆盖了所有质量维度，上述缺口属于"设计时难以自动化"的范畴。

## 4. CLAUDE.md 改进建议

### 建议 1: 新增"DB JSON 字段解析验证规范"（P1）

**问题**: parseMappingReason 格式 bug 的根因是前端解析器对 DB JSON 字段的格式假设错误。

**建议在 CLAUDE.md "代码品味原则"中新增**:

```markdown
| DB JSON 字段解析 | 解析 DB 中 JSON 字段的代码，测试必须使用 DB 实际序列化的数据格式（从 insertRequestLog 或实际 DB 读取），禁止凭假设构造测试数据 | parseMappingReason 测试数据与 DB 格式不一致 |
```

**理由**: 这是第 2 次出现类似问题（第 1 次是 `providers.models` 的 `parseModels()`），应固化为规则。

### 建议 2: Plan 伪代码验证要求（P2）

**问题**: Plan 中的 `parseMappingReason()` 伪代码直接假设了 `parsed.stages` 格式，编码实现者逐字实现。

**建议在 plan 编写规范中新增**:

```markdown
Plan 中涉及 DB JSON 字段解析的伪代码，必须标注其数据来源（如"pipeline_snapshot 由 insertRequestLog() 序列化，格式为 StageRecord[] 纯数组"）。
```

### 建议 3: 无需修改的规则

以下规则本次验证有效，无需修改：
- "数据消费者检查清单"规范 — Spec 中 12 个消费点全部列出，无遗漏
- "AC 覆盖矩阵"规范 — 9 AC 全部有测试覆盖
- "前端控件交互模式一致性" — Badge 使用 shadcn-vue 组件，符合规范
- "前端错误处理规范" — 无新增 API 调用，不涉及

## 6. 关键教训

### 教训 1: DB JSON 字段格式假设是最隐蔽的 bug 源

**现象**: `parseMappingReason` 假设 `pipeline_snapshot` 存 `{stages: [...]}`，实际存纯数组 `[...]`。
**根因**: Plan 伪代码、TDD 测试数据、实现代码三者共享同一个错误假设，TDD 无法检测。
**对策**: 
- 凡涉及 DB JSON 字段解析，**编码前**先从 DB 读一条真实数据看格式
- 测试数据必须使用与 DB 序列化一致的构造方法（如直接构造 StageRecord 数组后 JSON.stringify）
- Plan 中标注 JSON 字段的实际序列化来源

### 教训 2: 跨层穿透需求的 Spec 需要显式消费者矩阵

**现象**: 初始 Spec 质量不足以通过评审，需要 3 轮。
**根因**: "映射原因"从 resolveMapping() 到前端 Badge，穿透了 12 个消费点。这类需求的信息密度远超普通字段添加。
**对策**: 
- 当需求涉及"数据从后端某函数穿透到前端展示"时，Spec 必须包含完整的数据消费者检查清单
- 六要素覆盖矩阵作为 Spec 完成前的自检项

### 教训 3: 编码评审的独立验证价值

**现象**: TDD 测试全部 RED→GREEN，但 parseMappingReason 格式 bug 未被发现。
**根因**: TDD 保证"代码实现了测试期望的行为"，但当测试期望本身就是错的（基于错误假设），TDD 无法拦截。
**对策**: 
- 编码评审不应只看"代码是否匹配 plan"，还要独立验证关键假设
- 评审者应特别关注"与外部系统（DB、API）的接口边界"

### 教训 4: 并行 subagent 编码效率高

**现象**: Stage 10 编码实现（后端 6 Task + 前端 5 Task）仅用 14 分钟。
**成功因素**: 
- Task 拆分清晰（每个 1-2 文件），依赖关系明确
- 3 个并行 subagent（B1-B4 / B5-B6 / F1-F5）
- Plan 中每个 Task 有具体代码位置和修改方向
- TDD 先行提供了明确的 GREEN 目标

### 教训 5: L2 复杂度需求使用 L1 流程也能成功

**本次需求被评为 L2 复杂度**（跨后端 6 文件 + 前端 5 文件），但全流程在 150 分钟内完成，且只产生 1 个关键 bug（被评审拦截）。
Plan 的 Task 拆分和依赖关系设计是关键成功因素。
